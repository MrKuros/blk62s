# Elexon data: WINDFOR vs FUELHH (WIND)

Researched 2026-10-26. Sources: the official OpenAPI spec (`https://data.elexon.co.uk/swagger/v1/swagger.json`), the BMRS web pages, and empirical probes of the live API. "API probe" in the Source column means an empirical check against the live API; those one-off probe scripts are not included (the January checks are reproducible with `exploratory/jan_analysis.py`). The probes covered FUELHH for 2025-01-01..2026-02-02, WINDFOR publishes from 2023-01 to 2026-01, and January 2026 in detail.

## TL;DR

- **Coverage matches by definition.** Both series cover only wind farms that are visible to NESO and have operational metering, which is mostly transmission-connected BMUs. Both exclude embedded or distribution-connected wind. NESO puts operational-metered wind at about 82% of GB wind (2025). [1][2]
- **The measures do not match, and the gap is systematic.** In every month of 2025–Jan 2026, WINDFOR at 0–6 h lead sits 6–21% above FUELHH. In Jan 2026 the mean bias is +1.56 GW (MAE 1.79 GW). The bias grows with forecast level: about +0.5 GW when the forecast is 4–8 GW, +2.6 GW at 16–20 GW and +4.5 GW at 20 GW and above. This pattern fits WINDFOR forecasting available, unconstrained output while FUELHH meters output after curtailment (turn-down bids and constraints). **UNVERIFIED:** no Elexon or NESO document says what WINDFOR's constraint basis is.
- **Caveat the app states:** "Actuals are FUELHH metered output of operationally-metered (mostly transmission-connected) wind, about 82% of GB wind, after any curtailment. Forecasts are NESO's WINDFOR for the same metered fleet. Embedded wind is in neither. Some 'forecast error' at high wind is likely curtailment, not forecast skill." A firm-wind buffer built on FUELHH is still the right target for a buyer, because metered output is what actually arrives.

## API limits

- **No max range is documented for these endpoints.** Other endpoints state one (1, 7, 92 or 366 days), but the WINDFOR and FUELHH descriptions do not. [3]
- **Large requests work in practice:**
  - WINDFOR stream for 2023-01 to 2026-01 in one call: HTTP 200, 60 MB, 531,753 rows.
  - FUELHH WIND for 13 months in one call: HTTP 200, 3.4 MB.
  - A full month takes about 2 s for each dataset.
- The BMRS Wind page says the API serves "periods of up to two months". The API does not enforce this. [1]
- **Rate limits are undocumented** (**UNVERIFIED**). The spec lists `429 Too many requests` for both stream endpoints, but the API returns no rate-limit headers and needs no API key. An old Elexon API policy says requests "may be capped" as Elexon sees fit. [3][6]
- **Recommendation:** fetch January once at build time (about 2.4 MB of WINDFOR plus 0.3 MB of FUELHH) and ship it as static JSON. A live fetch can serve as an optional refresh, with backoff on 429.
- Calling `/datasets/WINDFOR/stream` with no parameters returns only the latest publish (73 rows).

## Joining for the app

- Keep publishes with `publishTime < cutoff(D-1)` (the app uses a strict `<`; see `market-timing.md`) and `startTime` within delivery day D. Take the latest such publish for each hour, or keep all of them to show lead time.
- Join on `startTime` against FUELHH, which gives hourly points. The app compares the hourly forecast with the mean of the two half-hours in that hour, with the other alignments as a sensitivity check.
- If the GB day-ahead auction closes around 09:20 UK time on D-1 (**UNVERIFIED** here; see `market-timing.md`), the latest usable publish in GMT is **07:30Z**. The 09:30Z publish comes after the cutoff.
